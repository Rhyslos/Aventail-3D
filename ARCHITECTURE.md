# Architecture

Aventail 3D is a Rust program split into small, single-purpose crates: the mesh at the bottom, the scene document in the middle, rendering and interface on top. **Lower layers never depend on higher ones**, so each piece can be built, tested and replaced on its own. The `layer-check` tool enforces this on every change.

Crate names are generic on purpose (no product name), so renaming the app never touches the code's structure; see [RENAMING.md](RENAMING.md).

## Layers

| Layer | Name | Crates | Rule |
| --- | --- | --- | --- |
| 4 | App | `app` | Wires everything together and owns the frame loop. No feature logic. Home of `branding.rs`. |
| 3 | Front end | `render`, `tools`, `ui` | Reads the scene; changes it only through commands. |
| 2 | Services | `fileio` | Talks to the outside world: project files, OBJ, glTF, the settings file. |
| 1 | Core | `scene`, `uv`, `booleans`, `paint`, `bake`, `matgraph`, `shapes`, `config` | The scene document, UV mapping, booleans, texture painting, maps baked from shapes, material graphs, vector shapes for the shape canvas, and settings. No files, GPU or UI. |
| 0 | Geometry | `mesh`, `words` | The polygon mesh and its operations, and the language layer every text goes through. Know nothing about the app; `words` depends on nothing at all, and `mesh` only on it. |

Each crate's `README.md` states its purpose and what it **must never** do. Read it before changing the crate.

Planned later: a `script` crate (layer 2, scripting (LustScript and Lua) through the same commands as everything else; Phase 14, see [decision 0011](docs/decisions/0011-lua-scripting.md) and [decision 0119](docs/decisions/0119-roadmap-after-the-uvs.md)), and animation support inside `scene` (Phases 17 and 18). Every text a person reads, in any crate, goes through one language layer, the `words` crate, with English as the one language package (`crates/words/lang/en.txt`) for now ([decision 0117](docs/decisions/0117-language-support.md), [decision 0132](docs/decisions/0132-one-language-layer.md), [decision 0134](docs/decisions/0134-shared-language-crate.md)).

## How a frame runs

The interface thread draws 60+ frames a second and must never wait on slow work.

1. **Input:** winit delivers mouse and keyboard events.
2. **Interpret:** the active tool (`tools`) turns input into an intent ("extrude these faces by 50 cm").
3. **Command:** the intent becomes an operation plus a command, applied to the scene. Every command can undo itself.
4. **Evaluate:** the object's stack is re-evaluated from the changed layer upward, using cached results below it. Inside the changed layer, it resumes from the longest run of unchanged edits, at a kept shape (after all the layer's edits, or all but the last), so adding, dragging or changing the last edit applies only that edit ([decision 0042](docs/decisions/0042-fast-edits.md)).
5. **Sync:** the renderer updates GPU data only for meshes that changed, and for a mesh whose points only moved, only the vertices around them.
6. **Draw:** viewports render with wgpu; panels (egui) draw on top.

Slow work (large unwraps, booleans, modifiers, saves and exports) runs on background threads. **Background jobs never touch the scene.** They send results as messages, and the interface thread applies them at the start of the next frame. Saves and exports (`app::file_work`, [decision 0163](docs/decisions/0163-saving-and-exporting-in-the-background.md)) work on a copy of the document taken when they start (`Scene::copy_with_results`: shapes shared, everything worked out kept), one at a time, and report back to the workbench, which says so in the status bar; closing waits for them.

## Startup

1. **Command line** (`app`): `--version` and `--help` print and exit; anything unknown is explained, with exit code 2; `--` ends the options, so a file name may start with `-`.
2. **Window** (`app` with eframe): open the window, named and identified through `branding.rs`, apply the theme (`ui::theme`; see [decision 0009](docs/decisions/0009-theme.md)), and restore the panel layout saved last time. See [decision 0008](docs/decisions/0008-window-and-panels.md).
3. **Each frame** (`ui`): the scene tabs (`ui::SceneTabs`) hand the frame to the tab in use's workbench, which draws the menu bar (with the tabs), the command palette, the mode palette, the status bar and the docked panels, and returns any actions (such as Quit) for the app to carry out.
4. **Closing**: eframe saves the window size and the panel layout (`app.ron`, in a per-user folder named after `APP_ID`).

## Window and panels

### Scene tabs

Several projects can be open at once, one **tab** each ([decision 0266](docs/decisions/0266-scene-tabs.md), plan in [docs/plans/scene-tabs.md](docs/plans/scene-tabs.md)). `ui::SceneTabs` holds a whole `Workbench` per tab (document, undo, selection, view, mode, layouts, caches and background work) and shows only the tab in use; the others are kept as they were. App-wide things (settings, libraries, recent projects) are handed from the tab in use to the next when it changes (`Workbench::take_shared_from`). The tab row is drawn by the workbench in use from a `TabStrip` and what is clicked comes back as events the tabs carry out after the frame; the workbench's actions come back paired with their tab (`(TabId, WorkbenchAction)`), so the app carries each out on the right project. The app keeps, per tab (`app::tabs`), the GPU renderer (all on the window's one device; dropped when the tab closes), the backup session and the emergency copy (children of the one the panic hook holds); one save or export runs at a time, reported to the tab that asked.

A tab left for another **sleeps** after the time chosen in Settings, or at once when the computer is low on memory ([decision 0267](docs/decisions/0267-sleeping-tabs.md)). Each frame the app asks `SceneTabs::sleep_tabs`, which puts due tabs to sleep: `Workbench::sleep` lets go of what the workbench worked out (the `DrawingCache`'s summary and shapes, the paint's `Composites`, the graph fills' maps and evaluator, the Material mode's pictures, a bake preview being made; background work on them is cancelled or left to finish and thrown away), and the app's `ViewportRenderer::sleep` (`GpuViewport`) lets go of the meshes, painted textures and view images on the GPU, keeping its pipelines (`render::ViewportRenderer::forget_scene`). Nothing the person made is touched, so waking is just showing the tab: the next frame works everything out again from the document. A tab whose save, bake or export is under way (`Workbench::stays_awake`) isn't put to sleep. The free memory comes from `app::platform::memory` (Windows and Linux), looked at by `app::memory::MemoryWatch` at most every ten seconds.

**Copy and paste between tabs** ([decision 0268](docs/decisions/0268-paste-between-tabs.md)). Copying objects keeps a `scene::Clipping` (`Clipping::capture`: the objects, what is inside them, the objects they read, their materials' texture sets, the graphs those run and the own boxes those use), shared by every tab through `Workbench::take_shared_from` and held in memory only. Pasting in another project (each project has a number in the run, `Workbench::project`) is `scene::Command::Paste`: `Clipping::plan` decides what to reuse and what gets new ids and names (own boxes through `matgraph::own::bringing`), and `scene::command::pasting` adds own boxes, graphs, texture sets and then the objects (each once the objects it reads are in), one undo step. The Material canvas's copied boxes carry their own boxes the same way. The tool still makes a command; nothing changes the scene directly.

```text
app (window)                          ui
  AllTabParts { TabId → renderer,      SceneTabs [ Workbench, Workbench, … ]
                backups, snapshots }      └─ the tab in use draws the window and the tab row
  carry out (TabId, action) ───────────► the tab's workbench
```

The `ui` crate's workbench owns everything inside the window:

```text
┌──────────────────────────────────────────────────────────────┐

│ Command palette (tools, primitives)                          │
├──┬──────────────────────────────────┬──┬─────────────────────┤
│M │ Viewport                         │Mo│ Attributes          │
│o │                                  │di├─────────────────────┤
│d │                                  │fs│ Objects, Edit layers│
│e ├──────────────────────────────────┴──┤                     │
│s │ Coordinates                         │                     │
├──┴─────────────────────────────────────┴─────────────────────┤

└──────────────────────────────────────────────────────────────┘
```

The five middle panels are dockable (egui_dock; Edit layers is a tab beside Objects, Levels a tab beside Attributes); the bars and palettes around them are fixed. The modifiers palette is drawn inside the viewport's panel, on its right edge, so it always sits between the viewport and the panels beside it ([decision 0091](docs/decisions/0091-edit-layers.md)). Palette icons are drawn in code (`ui/src/icons.rs`, with one file per family of icons in `ui/src/icons/`). The workbench never touches the window or files itself: it returns actions for `app` to carry out.

## Viewport

The viewport holds four views (perspective, top, front, right), each with its own `tools::Navigator`; it shows the active one, or all four in a 2 × 2 layout. Each frame, for each view shown:

1. **Navigate** (`ui` → `tools`): the panel turns this frame's drags (with the keys held) and wheel turns into plain moves on a `tools::Navigator` (the camera and its pivot); `tools::controls` decides which movement a button and keys start, for the scheme the user picked. `tools` knows nothing about egui.
2. **Ask** (`ui`): the panel works out its size in physical pixels and the camera's matrices (`tools::Camera`), and asks a `ViewportRenderer` for an image, with the point the camera looks at (the grid is drawn around it) and display options such as the grid level (1 m, 50 cm or 10 cm lines).
3. **Draw** (`render`, through `app`'s `GpuViewport`): the backdrop with its horizon, each object's mesh (kept on the GPU in its own space and placed in the world), the grid and lines are drawn into that view's own offscreen image (one per view, keyed by `ViewportView::slot`) on the window's GPU device. Flat (orthographic) views get a plain backdrop and a grid in the plane facing them.
4. **Show** (`ui`): the image is drawn into the panel as an egui texture, with the view's label on top.

While the mouse hovers over a view, the panel also asks the renderer what surface is under it (`ViewportRenderer::pick`); the answer arrives on a later frame and is used as that view's pivot when an orbit or zoom starts; only the view under the mouse asks, one question at a time ([decision 0017](docs/decisions/0017-picking-the-point-under-the-mouse.md)).

In the Points, Edges and Polygons modes, the element under the mouse is found on the CPU instead (`ui::components` → `tools::PickScene`), from the hovered view's camera and mouse position, after the views are drawn. The workbench turns the selected and hovered elements into a small `ComponentOverlay`, which the app uploads as a separate `render::Overlay` layer; a mouse move rebuilds only that layer, never the scene's shapes ([decision 0027](docs/decisions/0027-component-modes.md)). The edited objects' own edges and points are drawn with their meshes.

**Heavy shapes** ([decision 0035](docs/decisions/0035-heavy-meshes.md)). The work an action costs follows what it changes, not the size of the mesh:
- **Meshes** share their parts between copies until one changes them: points in chunks, faces in one flat list, attribute layers (hard edges among them). Tools make geometry through the mesh builder, which carries every attribute layer over ([decision 0043](docs/decisions/0043-attribute-layers-and-the-builder.md)). A recorded move copies only the chunks it touches, and `Mesh::moved_since` tells caches what moved. Connections (`Mesh::topology`) and the box around the points are kept with the parts they depend on.
- **Picking:** `tools::MeshPick` indexes one mesh in its own space (bounding volume hierarchies over its triangles, points, edges and polygon middles). The `ui` `ComponentTracker` keeps one per object, builds new heavy ones on another thread (`prepare`), updates them around moved points, and keeps its `PickScene` as it was while a drag is under way.
- **Drawing:** the app's `GpuViewport` keeps each object's `render::MeshGeometry` on the GPU in its own space (`ViewportRenderer::set_mesh`), works out heavy new ones on another thread, uploads only the vertices around moved points (`update_mesh`), and places objects each frame (`set_draws`, a uniform per object). Dense wireframes fade in the shader, and are left out when too dense to see.
- **The mesh check** in the Attributes panel runs on another thread for heavy shapes.
- **Triangles:** drawing, picking and the selection tint cut polygons into triangles with one function, `mesh::triangulate` ([decision 0057](docs/decisions/0057-after-phase-4-testing.md)), so what is picked is what is drawn. Triangles and flat polygons without dents take a quick path; bent and dented ones are cut along lines inside them. The cut is made when a mesh's geometry or pick index is built, and kept while only points move.

`tools/heavy/heavy-check.sh` times all of this on a 3-million-polygon shape at the end of each phase, and painting on a 4K texture set of 20 layers ([decision 0188](docs/decisions/0188-speed-with-big-textures.md)): strokes, undo and the history's memory.

**Big textures** ([decision 0188](docs/decisions/0188-speed-with-big-textures.md)). Painting's cost follows the tiles a change reaches, not the texture's size: `paint::Composite` looks only at tiles whose layers changed (compared with the layers directly), keeps per tile the mix of the layers under the one that last changed, and mixes many tiles on every core; `paint::paint_dabs` paints a frame's dabs together, each core taking rows of tiles; `scene::memory` counts a texture set change side by side when the layers are laid out alike.

Hidden polygons ([decision 0055](docs/decisions/0055-basics.md)) are a view setting kept by the workbench: the drawing cache gives each item a `shown` mesh without them, which is what the renderer draws and the pick index searches, while the whole `mesh` stays for the tools.

Selecting follows the same path ([decision 0029](docs/decisions/0029-selection.md)): the viewport only records what the mouse did (`selecting::Gesture`), and once the frame's drawing is known the workbench's `Selector` looks it up in the same `PickScene` and changes the document. Whole objects are selected through `Document::set_selection` (as the Objects panel does) and elements are kept per object in `scene::Document` and changed through `select_elements`; both record undo steps; the selection rules themselves (all, invert, grow, shrink, loops, rings) are pure functions in `mesh::selection`.

Moving, rotating and scaling ([decision 0030](docs/decisions/0030-transform-gizmos.md)) uses the same split. `tools::gizmo` does the maths (handles, hit testing, `Change`s); the viewport draws the gizmo and hands over `GizmoEvent`s; the workbench turns each frame's change into commands with `transforming::Session`. A session takes back its previous frame with `Document::abandon` and executes the whole change again under one merge key, so a drag is one undo step and one recorded operation, and cancelling is one more `abandon`. Commands the user can pick are listed once in `ui::commands` (name, icon, key, explanation, when it arrives); the tool menu (`E`), the menus, the palette and the keys read from that list, and the workbench carries any of them out through one `run_command` ([decision 0037](docs/decisions/0037-tool-menu-and-command-list.md)). Tools still never change the scene directly: objects move by `Command::SetTransforms`, and in the Object mode their pivots by `Command::MovePivots` ([decision 0068](docs/decisions/0068-pivot-editing-and-scene-units.md)), points by recorded `MovePoints` and `TransformPoints` operations, extrudes and insets by `ExtrudePolygons`, `InsetPolygons` and `ExtrudeEdges` ([decision 0038](docs/decisions/0038-extrude-and-inset.md)) and bent extrudes, spirals included, by `ExtrudeBent` ([decisions 0050](docs/decisions/0050-pipe-bends.md) and [0062](docs/decisions/0062-spirals.md)), bevels by `BevelEdges` and `BevelPoints` ([decision 0040](docs/decisions/0040-bevel.md); rounded corners and stopping at neighbours are `mesh::bevel`'s own work behind `BevelOptions::improved`, [decision 0141](docs/decisions/0141-improved-bevel.md), so old recorded bevels keep their shape), loop cuts by `LoopCut` ([decision 0047](docs/decisions/0047-loop-cut.md)), Connect, Bridge and Weld by `Connect`, `Bridge` and `Weld` ([decision 0051](docs/decisions/0051-connect-bridge-weld.md)), clean-up by `DeleteElements`, `Dissolve`, `FillHoles`, `FlipPolygons` and `FixFacing` ([decision 0052](docs/decisions/0052-clean-up.md)), hard and soft edges by `SetHardEdges` and `HardEdgesByAngle` ([decision 0053](docs/decisions/0053-hard-and-soft-edges.md)), materials by `SetMaterial` ([decision 0074](docs/decisions/0074-material-slots.md)), and slits by `Slit` ([decision 0049](docs/decisions/0049-slit.md), stored as a line in the object's own space, with no ids), whose drags work the same way (`workbench::modelling` and `workbench::loop_cut`, `viewport::tool_drag`; Loop cut and Slit take clicks too; Bridge and Weld take a drag only when it starts on a highlighted element, so clicks still select; `workbench::slit` keeps the line being drawn) and whose last one can be changed with `Command::ReplaceOperation`. Those also record `mesh::Anchors`, where their elements were, so when a base's new settings renumber its points the stack finds them again by position ([decision 0032](docs/decisions/0032-edits-find-their-points-again.md)). With symmetry on ([decision 0054](docs/decisions/0054-symmetry.md)), the target is mirrored when a change begins: `mesh::symmetry::mirror_plan` groups the points with their mirrors, and each group is recorded as its own move or transform in the same undo step. Every other modelling edit made with symmetry on is wrapped as `Operation::Mirrored` with the object's `mesh::symmetry::Mirror` (axes and middle, from `Workbench::mirror_for`) ([decision 0059](docs/decisions/0059-symmetry-for-every-edit.md)); `scene::mirroring` makes it on both sides when the shape is worked out, together or as mirrored copies.

Rendering sits behind the `ViewportRenderer` trait, so the panel runs in tests with no GPU. See [decision 0013](docs/decisions/0013-viewport-rendering.md).

## Axes

**Z is up**, right-handed: X and Y form the ground plane. Every crate that deals with positions (`mesh`, `scene`, `render`, `tools`) uses this; only `fileio` converts, to Y-up for glTF. See [decision 0012](docs/decisions/0012-z-up-axes.md).

## The scene

- The single source of truth for an open project: the object hierarchy, each object's base and its operation stack. See [decision 0006](docs/decisions/0006-base-plus-operation-stack.md).
- An object is a **base** (a parametric primitive, an imported mesh, or an editable mesh) plus a **stack of layers**, each holding recorded operations. Base parameters stay editable; the stack replays on top. Built so far ([decision 0021](docs/decisions/0021-object-stack-foundation.md)): the base is the object's kind (a primitive or a plain mesh), the stack a list of layers with one implicit *Edits* layer, and `Scene::evaluated` works out the final shape from a per-layer cache inside the scene, which also keeps each layer's shape before its last edit ([decision 0042](docs/decisions/0042-fast-edits.md)). Each recorded edit is an entry with an id and on/off and pinned switches; edits trust their ids while the structure below them is unchanged ([decision 0044](docs/decisions/0044-edits-that-hold.md)). The interface draws and frames evaluated shapes.
- Every mesh element has a stable ID that is never reused. Operations create IDs deterministically, so replaying an unchanged history gives identical IDs.
- The scene changes only through commands, which gives undo, redo and future scripting from one mechanism. Projects are saved and opened by `fileio` through a file model kept separate from the scene's types, so the scene can change without breaking old files ([decision 0024](docs/decisions/0024-saving-projects.md)); the interface asks the app to save or open, and the app shows the dialogs. While the app runs it also saves backup copies of the scene in the background: the workbench decides when (every interval while the scene changes, on its own clock separate from saving) and asks the app, which writes them on another thread into its own session folder, kept locked so the next start can tell a crash from a running app and offer the copies back ([decision 0036](docs/decisions/0036-autosave.md)). If the app panics, a panic hook (`app::emergency`) writes one more copy, the *emergency copy*, from a snapshot of the document the app keeps after each frame in which it changed (at most twice a second, behind a lock the hook only tries to take), so a crash loses at most a moment of work. An installed Windows copy also looks for newer builds on GitHub's Releases page and downloads one in the background (`app::updates`, through the system's curl); the workbench only shows the offer and returns `InstallUpdate`, and the setup program runs after the window has closed ([decision 0169](docs/decisions/0169-installer-and-updates.md)). Releases are made by `.github/workflows/release.yml` after CI passes on main, with the Inno Setup program from `installer/windows/`. Undo history is bounded by a memory budget, not a step count: 2 GB as standard, oldest steps forgotten first, the newest always kept ([decision 0022](docs/decisions/0022-undo-memory-budget.md)).
- **Built so far** ([decision 0018](docs/decisions/0018-scene-document-and-undo.md)): `scene::Document` holds the `Scene` (a tree of objects with stable ids that are never reused), the undo history and the selection. `Document::execute` carries out a `Command` as small reversible edits (insert, remove, relocate, rename, show/hide) and records them as one step; `undo` applies their opposites in reverse order. The workbench owns the document: the Objects panel, menus and keys hand it commands, and the viewport reads a summary: the shown objects' meshes, world placements and selection (rebuilt only when the scene or selection changes), and the boxes to frame. An object's shape comes from its kind: a primitive's settings build a `mesh::Mesh` ([decision 0020](docs/decisions/0020-primitives.md)); the app turns the meshes into one GPU shape when the drawing's version changes.
- Exports are prepared once (`fileio::export::prepare`: objects, polygons or triangles, normals as seen, UVs, in the file's units and up axis) and every format writer works from that ([decision 0071](docs/decisions/0071-obj-export-and-import.md)); polygons carry their material slot and objects their materials, joined by name across objects ([decision 0074](docs/decisions/0074-material-slots.md)). The workbench asks for an export or import with a `WorkbenchAction`; the app asks where (native dialogs; when one can't open, the workbench's path window asks instead, [decision 0164](docs/decisions/0164-interface-fixes-from-the-phase-10-testers.md)), calls `fileio`, and reports back. A project's game project folder (`scene::ExportTarget`, only text in the scene) is exported into by the app after each successful save, through `fileio::engine::export_into`, which never creates folders and only replaces the app's own files ([decision 0076](docs/decisions/0076-engine-export-paths.md)).
- **Live booleans** ([decision 0135](docs/decisions/0135-live-booleans.md)). An object's `booleans` name other objects (its cutters) and what they do; they change only through `Command::AddBoolean` and `Command::SetBooleans`. `Scene::cut_shape` works the cut out with the `booleans` crate (layer 1, wrapping `manifold-rust`): the evaluated shape, each cutter's whole shape placed into its space, rebuilt into polygons with their values; it is cached until anything it is made from changes. `Scene::unmodified_shape` is the cut with the live mirror after it, and what the modifiers start from; edits and picking keep working on `Scene::evaluated`. A heavy cut is handed out as a `CutJob` (`Scene::cut_state`), which the interface's drawing cache runs on another thread and gives back with `Scene::store_cut`, drawing the last cut meanwhile. Cutters are drawn as outlines (`DrawItem::outline`, `render::MeshDraw::faces` off) and left out of exports. The document keeps the order objects were selected in (`Document::selection_order`): the first selected is the one kept.
- **Modifiers** ([decision 0142](docs/decisions/0142-modifier-stack-and-remesh.md)). An object's `modifiers` (`scene::Modifier`: a `ModifierKind` with its settings, on/off, Show in viewport) are worked out after its edits, booleans and live mirror (`Scene::unmodified_shape`), first to last, for a `Purpose` (the viewport, or an export and Bake into shape); they change only through `Command::AddModifier`, `ChangeModifier`, `RemoveModifier`, `MoveModifier`, `DuplicateModifier` and `BakeModifiersUpTo` (bakes those up to one, keeping the later ones and their level changes, [decision 0168](docs/decisions/0168-modifiers-in-the-lists.md)). The scene keeps every step's result per object and purpose and reuses unchanged steps; `Scene::stack_state` hands out a `StackJob` for the rest, which the drawing cache runs on another thread when heavy (`MODIFIERS_IN_BACKGROUND_FROM`) and gives back with `Scene::store_stack`, showing the last result meanwhile. A source's own modifiers are never worked out while gathering it: the job does them first and hands them back with its own. The work estimate is kept while nothing changes, and the problems an export would have are worked out on another thread by the drawing cache for the selected objects (`Scene::export_problems_job`), never in the Attributes panel's frame. `Scene::shown_shape` is the viewport's final shape, `Scene::exported_shape` what exports and Bake into shape use. The work itself is pure functions in `mesh` (Remesh: `mesh::remesh`; Subdivide: `mesh::subdivide`, [decision 0143](docs/decisions/0143-subdivide-and-creases.md)). Each step gets a `ModifierContext` with the purpose and the object's Smoothing (`hardness`), both part of what its cached result was made from. Decision 0142 has the recipe for adding a kind.
- **Creases** ([decision 0143](docs/decisions/0143-subdivide-and-creases.md)). A mesh edge layer (`mesh::crease::CREASE`, 0 to 1) set by a recorded edit, `Operation::SetCreases`, like hard edges and seams; the Subdivide modifier reads it from its input. The interface records it from Crease edges and Uncrease (`workbench/creases.rs`) and the Attributes panel's Crease field, which replaces its own edit while one drag lasts (`Command::ReplaceOperation`, one undo step).
- **Lattice cages and deformers** ([decision 0144](docs/decisions/0144-lattice-cage.md)). A cage is `ObjectKind::Lattice` (a `mesh::lattice::Lattice`: divisions, a box, points, interpolation), an object with no shape of its own (`has_shape` false: never exported, edited, cut or modified). Each shape it bends has a `ModifierKind::Lattice` naming it; the stack hands the modifier its source as `SourceData::Cage` (sources carry a shape or a cage), and the modifier moves the shape's points through the cage's space with `mesh::deform::deform`, the groundwork bend, twist and taper reuse (a `Deformer`, an `AxisRange` or `BoxRange` it works over, everything but the points kept). `Command::AddLattice` fits a cage and adds the modifiers in one step; `Command::EditLattice` changes it. The interface draws a cage as overlay lines (`DrawItem::cage`), picks its lines in front of surfaces, and in the Points mode gives a selected cage's points as loose points, so selecting, the gizmo and Coordinates work unchanged (`PointsStart::cage` turns the change into a cage edit). Saved in file format version 45.
- **Decimation** ([decision 0145](docs/decisions/0145-decimate.md)). `ModifierKind::Decimate` runs `mesh::decimate`, quadric error collapse that keeps UV seams, hard edges (as the object's shading shows them, through `ModifierContext::hardness`), material borders and open borders as lines. Its `Decimator` goes on from one target to the next, so the LOD generator can make nested levels at the cost of the smallest alone (`decimate_levels`).
- **Scatter** ([decision 0146](docs/decisions/0146-scatter.md)). `ModifierKind::Scatter(ScatterSettings)` runs `mesh::scatter`: the surface with copies of its sources (the other shapes it reads, each its final shape with its pivot and material renumbering in `SourceShape::pivot` and `materials`) on points, polygon centres or a random spread by area. Deleting a source changes the modifier through `ModifierKind::without_sources` (a scatter loses that shape, and goes with its last); `ModifierKind::work_with` counts the sources' polygons, so a heavy scatter is worked out on another thread.
- **Bend along curve and Shrinkwrap** ([decision 0147](docs/decisions/0147-curve-deform-and-shrinkwrap.md)). Two deformers reading another object (`scene/src/wrap.rs`). `ModifierKind::BendAlongCurve` reads a curve object as its line (`SourceData::Curve`, not its solid) and runs `mesh::curve::bend::bend_along` with the object's own pivot (`ModifierContext::pivot`, passed only to kinds whose `reads_pivot` says so, so moving a pivot reworks nothing else). `ModifierKind::Shrinkwrap` reads a target's final shape and runs `mesh::shrinkwrap::shrinkwrap` over a `mesh::bvh::TriangleTree` (a tree of boxes for nearest-point and line queries, reusable by later tools); its cost (`work_with`) counts the target's polygons.
- **Weighted normals and custom normals** ([decision 0148](docs/decisions/0148-weighted-normals.md)). Normals can be stored per polygon corner: `mesh::custom_normals` is a corner layer (`custom_normal`, a direction or none) that `mesh::corner_shading_with` uses in place of the worked-out normal, so the viewport (`render::MeshGeometry`, which then never updates moved points in place), exports (`fileio::export::export_mesh`: glTF `NORMAL`, OBJ `vn`), the MikkTSpace tangents made from them and `mesh::hardness::shading_hard_edges` (the bake check, Seams from hard edges) all follow with no code of their own. They fit only the shape they were made for: a recorded edit that changes points, polygons or hard edges drops them (`scene::stack::apply_from`, `custom_normals::shading_unchanged`), as do the live mirror and booleans, and every modifier after the one that made them (`StackJob::run`, unless `ModifierKind::carries_custom_normals`). `ModifierKind::WeightedNormals` runs `mesh::weighted_normals` (each corner's smooth group, by the object's Smoothing through `ModifierContext::hardness`, weighted by polygon area, corner angle or both, raised by Face influence, blended by Strength); `Scene::final_weighted_normals` and `normals_dropped_by` (`scene/src/weighted.rs`) tell the bake check and the Attributes panel whether its normals reach the export.
- **Live bevel and bevel weights** ([decision 0149](docs/decisions/0149-live-bevel.md)). `ModifierKind::LiveBevel` runs `mesh::live_bevel`: it chooses edges (sharper than an angle, hard as `ModifierContext::hardness` shows them, or marked with a bevel weight) and bevels them with the improved bevel (`bevel::bevel_edges_weighted`, each edge its weight's share of the width). `ModifierKind::goes_before` puts a new Live bevel before any Subdivide or Weighted normals, the recommended order (the bevel's result has no custom normals, so Weighted normals after it shades the bevelled shape). Bevel weights are a mesh edge layer (`mesh::bevel_weight`, sharing `edge_weights` with creases) set by `Operation::SetBevelWeights`; the interface's Crease and Bevel weight fields share their code through `ui::edge_values::EdgeValue`. File format 50.
- **Collision shapes** ([decision 0151](docs/decisions/0151-collision-hulls.md)). Not a modifier: the object's Collision setting gains *Wrapped in parts* (`Collision::Parts`, settings `Object::collision_parts`). `mesh::hull` (quickhull) and `mesh::convex_parts` (a V-HACD-style split on Remesh's voxels) make the hulls; `scene::collision` works out an object's shapes from a shape it is given and keeps them (`Scene::collision_state`, `CollisionJob` for another thread); the interface's component overlay (`ui/src/components/collision.rs`) outlines them from the drawn shape, and `fileio::export::collision` adds the parts to Godot exports from the exported shape as `name-partN-convcolonly` nodes. File format 52.
- **Quadify** ([decision 0150](docs/decisions/0150-quadify.md)). `mesh::quadify` chooses pairs of triangles (`pairs`: every edge of two same-way triangles not kept by seams, UV splits, hard edges as a `Hardness` shows them, materials, creases or bevel weights, within the angle and distortion limits) squarest first, and joins them with `cleanup::merge` (lower id kept, corners' values carried by the `Builder`). The squareness test and the greedy best-first pairing (`quadify::pairing`) are shared with Decimate's Quads where flat. It is both `ModifierKind::Quadify` (Clean up; `goes_before` Live bevel, Subdivide and Weighted normals) and a recorded edit, `Operation::Quadify { faces, options, hardness, anchors }` (no faces: the whole shape; the object's Smoothing stored in the edit, since edits are worked out without their object), whose settings are `EditSettings::quadify` under Last edit; the interface's one-off is `workbench::quadifying` (Mesh → Clean up). File format 51.
- **Weld by distance** ([decision 0152](docs/decisions/0152-weld-by-distance.md)). `mesh::weld_distance` groups points within a distance through a hash grid of cells that wide (`weld_groups_of`: lowest id first, each kept point taking every untaken point within the distance, no chains; with `only_borders`, points on open borders only) and welds them with Weld's own `join::weld_groups` (kept point stays put; corners' values carried by the `Builder`; collapsed polygons and orphaned points go); with `keep_seams`, joins where the UVs split are marked seams on shapes that have seam marks. `weld_by_distance(mesh, points, options)` is the in-place function the array modifier calls to join its copies. It is both `ModifierKind::WeldByDistance` (Clean up; `goes_before` Decimate, Quadify, Live bevel, Subdivide and Weighted normals) and a recorded edit, `Operation::WeldByDistance { points, options, anchors }` (no points: the whole shape), whose settings are `EditSettings::weld` under Last edit; the interface's one-off is `workbench::welding_distance` (Mesh → Clean up). File format 53.
- **Array** ([decision 0153](docs/decisions/0153-array.md)). `ModifierKind::Array(ArraySettings)` (`scene/src/array.rs`) runs `mesh::array`: one matrix per copy (`copy_matrices`: a line's step, a grid's steps, a ring's turns round a centre), the first copy the input itself with its ids, the rest appended with `parts::append`, then, with Merge, `weld_distance::weld_by_distance` on open borders only. A ring's centre is the object's pivot (`reads_pivot`) or a source object read only for where it stands (`SourceData::Place`, so any object can be one and its shape is never worked out for it); deleting it puts the ring back on the pivot (`without_sources`). *UVs side by side* shrinks each copy's UVs into a square of its own.
- **Shell** ([decision 0154](docs/decisions/0154-shell.md)). `ModifierKind::Shell(ShellOptions)` runs `mesh::shell`: per-point offsets (`shell::offsets`, the angle-weighted facing, or with Even thickness the least-squares offset meeting every polygon round the point at the thickness, at most `MAX_STRETCH` times it), the surface kept with its ids and moved by the front share, a copy turned round through the builder and moved by the back share, and a rim quad per open border edge (`shell::rims`: hard and seam edges, a row of UVs per strip above the texture square). `goes_before` puts a new Shell before Live bevel, Subdivide and Weighted normals, and a new Weld by distance before a Shell. File format 55.
- **Levels of detail** ([decision 0155](docs/decisions/0155-levels-of-detail.md), [decision 0165](docs/decisions/0165-levels-panel.md)). Not a modifier: `Object::lods` (`scene::lod::Lods`, set by `Command::SetLods`). Each level is made from `Purpose::Level(k)` (the export's stack with the level's `ModifierOverride`s, keyed by each modifier's stable `ModifierId`, reusing the export's steps before its first change), the exported shape, or a shape made by hand (an ordinary object inside the object, `Command::MakeLevelByHand`, `RestartLevel`; drawn only while selected, in the object's place, so every editing mode, picking and gizmo works on it with no code of its own), then reduced with `mesh::decimate::decimate_levels` (levels from the same shape nested). The scene keeps them (`Scene::lod_state`, `LodJob` for another thread, `lods_if_ready` for the Levels panel); the drawing cache (`ui/src/drawing/lod.rs`, `drawing/levels.rs`) draws the previewed level, and `fileio::export::lods` adds each level's real shape to exports when `ExportOptions::lod_levels` is on, never a hand-made level's shape as an object of its own. The interface's Levels panel is `ui/src/attributes/levels_panel.rs` (`Panel::Levels`).
- **Game bevel** ([decision 0156](docs/decisions/0156-game-bevel.md)). Not a modifier: a command composed of existing ones, `scene::Document::game_bevel` (`scene/src/game_bevel.rs`), run as one undo step (one history key): for each object, `Operation::HardEdgesByAngle` at its angle and `Command::SetHardness(Marked)` if it was smoothed by angle (a curve only switches), a Live bevel with `LiveBevelOptions::soften` added or an existing one's switched on, and Weighted normals added at, or moved to, the end and switched on; a refusal part-way abandons the step. `soften` (`mesh::live_bevel`) marks the chosen two-polygon edges soft on the bevel's input copy, so a hard edge's strip gets no hard borders, live, which also covers boolean cut edges (marked hard after the edits). The Live bevel's improved bevel also slides plain edges fanned between bevelled ones at a closed corner (`mesh::bevel::fans`, only through `bevel_edges_weighted`, so recorded Bevel tool edits replay unchanged). glTF export gives a corner without a MikkTSpace tangent a unit one square to its normal. File format 57.
- **Displace** ([decision 0157](docs/decisions/0157-displace.md)). `ModifierKind::Displace(DisplaceSettings)` (`scene/src/displace.rs`: the options and the chosen point ids) runs `mesh::displace`: each point pushed by `noise::layered` (hand-written gradient and cell noise hashed from the cell's place and the seed with `names::mix`, in Detail layers) times Strength, along `shrinkwrap::point_normals` or an axis, times its falloff share round chosen points (`displace/falloff.rs`, Dijkstra along the edges). The point loop is `deform::with_points_moved`, which `deform` uses too. `goes_before` Weighted normals; `work` is points × layers ÷ 40.
- **Bend, twist or taper** ([decision 0158](docs/decisions/0158-bend-twist-taper.md)). `ModifierKind::BendTwistTaper(AxisDeformOptions)` runs `mesh::axis_deform` through the lattice's `deform` groundwork: the deformer's space is the object's pivot (read through `reads_pivot`) moved by Centre, the chosen axis as Z; limits are shares of the input's length along it, past which the shape carries on rigidly. The viewport's helper comes from `Scene::deform_helpers` (measured on each step's cached input, `Scene::modifier_input`) and is drawn by `ui/src/components/deform_helper.rs` as `OverlayStyle::Helper` overlay lines with the guides, as collision outlines are, which the app hands to the renderer as lines on top (`render::Overlay::line_on_top`, no depth test), since the axis runs through the shape. `goes_before` Weighted normals; `work` is points ÷ 20.
- **Struts** ([decision 0159](docs/decisions/0159-struts.md)). `ModifierKind::Struts(StrutsOptions)` runs `mesh::struts`: a closed prism per edge and a closed faceted ball per used point (`struts/pieces.rs`, both rings of a regular profile with end polygons), overlapping rather than welded, so any input works; each piece is a UV island (`struts/layout.rs`: rings unrolled as rows, ends hung off them, shelf-packed at one texel density). With *Keep the faces* the input is kept with its ids and the struts' UVs go in the square above. `goes_before` Live bevel, Subdivide and Weighted normals; Weld by distance and Quadify go before it. Named apart from the viewport's Wireframe look. File format 60.
- **Modular kit helpers** ([decision 0160](docs/decisions/0160-kit-helpers.md)). Not a modifier. The project's `scene::KitGrid` (step and Kit-sized shapes, standard 1 m and off) is part of the scene like its units, changed by `Command::SetKitGrid`. `mesh::Primitive::fitted_to_grid` rounds a primitive's outside sizes to whole steps (sizes under half a step kept, round shapes by diameter, inner parts in proportion) and `scaled` multiplies every length; **Size to kit grid** (`ui::workbench::kit`) is a `SetPrimitive` per selected primitive under one merge key, and Kit-sized shapes goes through `Workbench::new_primitive`, which every way of creating a primitive uses. Snapping to it is a Snap setting (`SnapSettings::kit_grid`, `transforming::move_step`). The pivot presets are ready-made `MovePivots` placements at a point of the shape's own box (`Workbench::box_point`), a group in the Edit pivot ring and a Tools submenu. File format 61.
- **Triangles** ([decision 0161](docs/decisions/0161-triangulate.md)). One cut for everything: `mesh::face_triangles` (decision 0057) is what the renderer draws, picking finds, the export writes, **Display → Show triangles** draws (`mesh::triangulate::inner_lines`, kept per object by `ui/src/components/triangles.rs` while its drawn shape is the same `Arc`, drawn as `OverlayStyle::Triangle` under every other guide) and the **Triangulate** modifier's *Fixed* bakes (`mesh::triangulate::triangulated`: each polygon's first triangle keeps its id, the rest are new through the builder, every corner value copied). *Beauty* (`triangulate/beauty.rs`) turns lines inside flat parts to the other diagonal where that widens the thinnest corner. `ModifierKind::Triangulate` is in the Game ready family, every other kind `goes_before` it, and it carries custom normals (`carries_custom_normals`, `keeps_shading`), so `Scene::final_weighted_normals` looks past it. Saved in file format 62.
- **Curves** ([decision 0138](docs/decisions/0138-curves-sweep-lathe.md)). A curve object's kind (`ObjectKind::Curve`) holds its Bézier curve (`mesh::curve::Curve`, ready-made or points with stable ids) and its solid (a line only, a sweep or a lathe), changed only through `Command::EditCurve`, `SetCurveSolid` and `SetReadyCurve`. The solid is its base shape, built by `mesh::curve::sweep` and `lathe` (rotation-minimising frames) whenever it is evaluated, so it is drawn, cut, mirrored, exported and baked like any shape; a sweep taking another curve as its cross-section is evaluated with that curve, kept by the cache to tell when it changes. A curve takes no recorded edits. The interface draws every curve's line in the component overlay and, in the Points mode, gives a selected curve a mesh of loose points named by its parts, so the selection, picking and gizmo machinery work on it unchanged; Draw curve (`workbench::curve_drawing`) inserts one object when the curve is finished. Spline editing ([decision 0139](docs/decisions/0139-spline-editing.md)) adds `CurveEdit`s that keep the shape (insert by de Casteljau, delete stretching the neighbours' handles, extend, reverse, round corners, resample, close ends) and point handle kinds (`PointKind`, auto handles settled after every edit), plus `mesh::curve::join` and `split`, with the scene commands `JoinCurveEnds` and `SplitCurve` and `Join` on curves alone; the interface's curve commands live in `workbench::curve_commands`, the line double-click in the selector, carrying a curve on in `curve_drawing`.
- Transforms are stored relative to the parent; world transforms are always derived. An object's transform places its pivot; its `offset` places its shape relative to the pivot, so the shape's place in the world is `Scene::shape_matrix` (pivot × offset). Anything that works with a shape in the world uses that, not `world_matrix` ([decision 0068](docs/decisions/0068-pivot-editing-and-scene-units.md)).

## Material graphs

Phase 12 ([decision 0256](docs/decisions/0256-material-graph-plan.md), the plan in [docs/plans/phase-12.md](docs/plans/phase-12.md)) makes materials as node graphs. The engine is the `matgraph` crate (layer 1, [decision 0257](docs/decisions/0257-material-graphs-core.md)); it knows nothing of the scene, files, the GPU or the interface.

- **What a graph is:** `matgraph::Graph`: boxes (a kind's id, a place on the canvas, settings changed from their standard, by key), wires from an output plug to an input plug (one per input, by plug key), comment frames (title, colour, rectangle, note), a name and a seed. Box and frame ids come from one counter and are never reused.
- **Kinds of box** sit behind one trait, `BoxType` (`info()`: plain name, group, "What does this do?", plugs with their `ValueKind`, settings schema, what usually comes next; `run(&Job)`), listed in a `Registry`. A new box is one file in `matgraph/src/boxes/` and a line in `boxes::standard`. Ids (box, plug, setting) are saved in files and never change.
- **Value kinds:** shape, height, colour, whole material (`MaterialMaps`: colour, height, roughness, metal, normal, occlusion, curvature). `kind::fit` says whether one goes into another as it is, converted with a note, or not at all, with the reason.
- **Changes:** only through a checked `GraphEdit` (`Graph::apply`). A refusal is a `Refusal`: the reason in plain words and `Fix`es as data (a box to put between, another output to connect, the nearest value or size), for the interface to offer. The scene keeps the project's graphs (`Scene::graphs`, a `matgraph::GraphStore` by `GraphId`, each graph shared) and records `Command::AddGraph`, `SetGraph` and `EditGraph` as `Edit::SetGraph` undo steps, before and after shared.
- **Working out:** `Evaluator::run(registry, graph, size, wanted)` runs the boxes asked for and what feeds them, each after its inputs. Each box's result is cached under a hash of its kind, settings, size, seed and its inputs' own keys, so a change works out again only that box and those after it; results not used by the last run are forgotten past a memory budget. Each box shares its pixels over the cores in bands of 64 rows, so results don't depend on the number of cores. Every picture wraps round at its edges (`Image::at`) and every pattern repeats a whole number of times, so textures tile seamlessly. A box that can't run gives its `Refusal` and the rest still runs. The interface runs the evaluator on another thread (`ui::material::pictures`).
- **The interface** ([decision 0258](docs/decisions/0258-node-canvas.md)): `ui::material` is the Material mode. Its canvas reads the graph from the scene each frame and changes it only through `Command::EditGraph` (several edits as one undo step with `Document::execute_all_labelled`; drags merge under one key). Each change is checked on a copy first, and the tidy layout's moves (`material::tidy`, a pure function of the graph) are added to the same step. Refusals become a note with the `Refusal`'s fixes as buttons. A worker thread (`material::pictures`) works out the newest graph sent (small while it changes under a held button; a button held without a change, as when panning, makes no work) and sends back the `Evaluation`; the canvas makes each box's picture a texture only when it changed. Over the canvas its keys are taken before the rest of the app's.
- **The boxes** ([decision 0259](docs/decisions/0259-first-material-boxes.md)): 23 standard boxes (28 with milestone 5's From the model boxes, 29 with milestone 9's Scatter, 37 with milestone 10's) in `matgraph::boxes`, one file each, sharing `boxes::pattern` (a soft blur, the exact distance to an outline that wraps round, a random number per wrapped cell). Settings that are sizes are `SettingKind::Length` in centimetres; `Job::length_px` turns them into pixels with the graph's real-world size, which the evaluator reads from Material out (`eval::real_size_cm`) and hashes only into boxes with a length. Gradient map's colours are a `SettingKind::Gradient` (`ColourGradient`, 2 to 8 colours), edited in Attributes by `box_rows::gradient_editor`.
- **Preview and checks** ([decision 0260](docs/decisions/0260-preview-and-checks.md)): the Material mode's preview (`ui::material::preview`) lays the material on the selected model, a ball or a cube by their UVs at the real-world size (`material::laying`: repeats from `mesh::uvs::average_density`, the material repeated into a `PaintedTexture` with its realism maps) and has the views' renderer draw it through `ViewportRenderer::render_preview`, which the app answers with a second `GpuViewport` on the same device, so the views' shapes and textures stay on the graphics card. The seam check is `matgraph::SeamCheck`; the texture budget (`material::budget`) counts the maps from `fileio::export::maps_going_out`, the rule the painter's export uses too.
- **Graphs in the painter** ([decision 0261](docs/decisions/0261-graphs-in-the-painter.md)): a paint layer can be a graph fill (`paint::GraphFill` on `Layer::graph`: the graph's id, the layer's own values of the settings the graph shows in the painter, `GraphBox::shown`, and a hash of what its pixels were made from). `ui::workbench::paint_graphs` compares that hash with what the layer would be made from now (the graph with the layer's values, the texture size, the model's layout key, the repeats from `material::laying::repeats`, the realism switch) whenever the scene or drawing changes, and makes a layer that differs on another thread: `bake::model_maps` bakes the maps the graph's From the model boxes read (kept per material), then `bake::graph_fill` runs `Evaluator::material_on_model` (`matgraph::model`): boxes nothing from the model feeds make the repeat, the rest work on the model's texture square with repeats laid across it (`Value::repeated`). The pixels join the change's undo step with `execute_with_last` only if nothing changed meanwhile. The layer is ordinary paint after that, so masks, blending, the composite and the texture export need nothing new.
- **Baked export** ([decision 0262](docs/decisions/0262-baked-export.md)): a material given a graph (`ui::material::giving`, `ui::workbench::graph_giving`) is a texture set holding one graph fill, so `paint_graphs` makes it on the model and the texture export (`fileio::export::textures`) bakes it with every preset; nothing new flows. A graph alone goes out through `fileio::export::graph_textures` (`texture_set`, `write_set`): `Evaluator::material` at the texture budget's size on another thread (`ui::material::export_set`), then the maps by `maps_going_out`, packed, encoded and written safely, with a Godot `.tres` (`bake_file::godot_material_with`). `matgraph::bake_notes` says what a bake changes (animated boxes, From the model boxes off a model) or what stops it.
- **Your own boxes** ([decision 0263](docs/decisions/0263-your-own-boxes.md)): a project's own boxes live in `matgraph::GraphStore` beside its graphs, which also keeps **the project's registry** (`GraphStore::registry`: the standard boxes and an `own::OwnBoxType` per own box, each added after the own boxes inside it, so none can run itself). Everything that checks or works out a graph (scene commands, the canvas, the painter's graph fills, exports) uses that registry, not `Registry::standard()`. A placed own box's kind is the definition's id, so placed boxes are linked; `OwnBoxType::run` works the inside out with `Evaluator::run_given` (what is plugged in, the outer graph's seed and real-world size), and its cache key includes `BoxType::version` (a hash of the definition and those inside it). Making one (`own::Proposal::make`) and opening one up (`own::open_up`) are plain `GraphEdit`s plus a `Command::SetOwnBox`, carried out as one undo step by `ui::material::MaterialEditor::run_with`; changes inside are `Command::EditOwnBox`. Inside one, the canvas's pictures come from `Evaluator::run_inside` (the outer graph's inputs worked out first). Box files (`fileio::own_box_file`, JSON) and the library kept with the app's settings use the same stored form as the project (`project::v98`).
- **Tiling and boxes on any kind** ([decision 0270](docs/decisions/0270-tiling-and-moving-colours.md)): a graph fill's `tiling` (set from Attributes → Materials or the graph fill's settings, `ui::material::tiling`) goes into `paint_graphs`' made key and on to `bake::graph_fill`, which works the graph out with `OnModel::new(maps, repeats).with_tiling(tiling)`: the repeat is laid `repeats × tiling` times across the model's square, while boxes on the square keep the model's size (`square_cm`). The Material mode's Model preview lays it the same way (`laying::tiled`, `giving::tiling_on`). Transform and Repeat move a height, a colour and a material (`matgraph::boxes::moving`); a box may leave an output empty (`BoxType::run_outputs`, `BoxResult::outputs` as `Option`s) and need any one of its inputs (`BoxType::needs_an_input`), both checked by the evaluator with refusals that say why.
- **Scatter** ([decision 0271](docs/decisions/0271-scatter.md)): `matgraph::boxes::scatter`, the first Detail box. `scatter::placing` decides the copies on one core from the seed (`place`: at random or a grid fitted to whole rows, Keep apart through a cell grid with wrapped distances, the Where shape sampled at each copy's middle, capped at `MAX_COPIES` and `MAX_DEPTH`), and `Lookup` lists, per cell about a copy's reach wide, the copies reaching into it with their middles moved by whole textures over the edges. The box then fills one `Hit` per pixel (the copy on top by height, where on it, how much it covers, the highest height) over the cores, and makes each output from those. Outputs for the colour and material are `None` unless plugged in (`run_outputs`, decision 0270).
- **More boxes** ([decision 0272](docs/decisions/0272-more-boxes.md)): Cracks, Chips, Scratches, Fill the gaps (Detail), Brush strokes, Edge highlight, Directional light (Colour) and Slope blur (Shape), one file each in `matgraph::boxes`. Scratches and Brush strokes place their lines and strokes with `scatter::placing`; Slope blur takes any kind as Transform does (`moving`). The light-and-shade maths lives in `matgraph::light` (`sun`, `lit`, `warmed`), called by both the Directional light box and `paint::Lighting`, so a graph and the painter light alike. `graph::connect::boxes_between` leaves out boxes that take the wanted kind themselves (they only pass it on).
- **The shape canvas** ([decision 0273](docs/decisions/0273-shape-canvas.md)): the **Shape** box (`matgraph::boxes::drawn_shape`) keeps a `shapes::Drawing` on its `GraphBox::drawing` (only kinds whose `BoxType::takes_drawing` says so), changed only by `GraphEdit::SetDrawing`, so the canvas's every change is one `Command::EditGraph` (a drag one undo step under one merge key) and saving, copying and own boxes carry it with no path of their own. The `shapes` crate (layer 1, on `kurbo` and `tiny-skia`) holds the paths, pieces (Add, Cut, Line), mirror line and reference image, checks every change, and fills drawings at any size wrapping round the edges (`raster`); the box's job gets the drawing (`Job::drawing`) and its key (not the reference image's) goes into the box's cache key. The interface's `ui::material::shape_canvas` takes the node canvas's place while open (Tab back), drawing the filled shape, outlines and gizmos itself and showing the box's three outputs through `drawn_shape::drawn`. Saved from file format 100 (`fileio::project::v100`).
- **Assemblies** ([decision 0274](docs/decisions/0274-assemblies.md)): a `shapes::Piece` keeps its shape (`path`) apart from where it is placed (`place`), so linked copies (pieces with one `LinkId`) share one shape, every change to it made to all through `Drawing::with_path` / `with_shape` / `with_kind`, while moving, turning, sizing and flipping change only each piece's place. Groups keep their pieces together in the order. `Drawing::drawn_paths` is still the one place a piece becomes what is filled; `raster::layers` lays each piece's colour and height for the Shape box's Colours and Height. Everything is still one `GraphEdit::SetDrawing`; pieces copied are kept in `MaterialEditor::pieces_clipboard`, shared by every tab. Saved from file format 101.
- **Edges, varied copies and veins** ([decision 0275](docs/decisions/0275-edges-and-variation.md)): a piece's edge, varying and vein are shared by its linked copies (`Piece::same_shape`); its seed is its own. `Drawing::drawn_paths` (now in `shapes::drawing::variety`) places a piece, varies it (`Drawing::variation`: a group by its bottom piece), roughens its outline (`shapes::edge::edged`, a pattern repeating a whole number of times round it) and mirrors it, so the pictures, the canvas's outlines and clicking all see the same toothed shape; nothing toothed is stored. `raster::veins` gives the Line pieces' grooves and shading, which the Shape box adds to its Height and Colours.
- **Foliage output** ([decision 0276](docs/decisions/0276-foliage-output.md)): whole materials carry optional `opacity` and `translucency` maps (`matgraph::MaterialMaps`; `None` is solid, so nothing saved changes); the **Opacity** box makes them. `shapes::Sheet` (in `shapes`, which now uses `uv::pack`, same layer) lays a drawing's cards out on a leaf sheet; `raster::*_on` fill the moved outlines, and the Shape box's Layout picks it. The opacity flows out through `fileio::export::graph_textures` (the colour's alpha; `_Opacity`, `_Translucency`, Unity's `_Thickness` by `maps_going_out`; Godot's `.tres` by `bake_file::godot_card_material`) and into the preview as the laid texture's alpha, which `ui::DrawItem::cut_out` → `render::SurfaceDraw::Painted::cut_out` makes the shader discard under a half.
- **Animated materials** ([decision 0277](docs/decisions/0277-animated-boxes.md)): every box's `matgraph::Job` carries a moment (`Job::time`): the evaluator's (`Evaluator::set_time`, the preview's player) or else the graph's own (`Graph::moment`, what exports and the painter bake, since they set none). Only boxes with `BoxInfo::animated` (Time, Scroll, Pulse, Flow, and own boxes holding one) hash the moment into their cache key, so what they don't feed stays cached as time goes on. The player (`ui::material::player`) sends `PictureJob::time` to the pictures' thread each frame, newest only. Settings marked "change in the game" (`GraphBox::in_game`) and the moment are saved from file format 103 and reported by `matgraph::bake_notes` for the engine translators to come; no engine shader runs in the app.
- **Find and minimap** ([decision 0279](docs/decisions/0279-find-and-minimap.md)): `matgraph::Graph::find(registry, query)` (`graph/find.rs`) lists the boxes and frames matching every word typed (box names through the project's registry, chosen choices, shape pieces' names, frames' titles and notes) as `Found`s in reading order. The ui's `material/finding.rs` keeps the search on the canvas (`Canvas::finding`), found again only when the words, the graph or the registry change (`Arc`s compared), and goes to a match by selecting and framing it (no edit, no undo step). `material/minimap.rs` maps the graph's extent and the part on screen (`MapPlace`) in the canvas's corner, drawn from `Places` so wires bend through their dots as on the canvas; it is a canvas overlay, so the canvas takes no press on it, and keeps its place while dragged (`Canvas::map_drag`).
- **Variations and the dice** ([decision 0280](docs/decisions/0280-variations-and-the-dice.md)): a graph keeps named looks (`matgraph::Variation`: the shown settings, every seed and the moment; `graph/variations.rs`), changed by three `GraphEdit`s and saved with it (file format 105). Using one is the plain setting, seed and moment edits it stands for (`Graph::variation_edits`), run as one undo step; the dice are the seed edits `Graph::rolled` makes from a repeatable roll. A graph fill (`paint::GraphFill::variation`) runs `Graph::with_variation` before its own values; the painter makes layers from the graph without its variations, so saving one makes nothing again. The ui's `material/variations.rs` holds the canvas bar's menu and dice, the Attributes rows and the painter's picker.
- **Project palettes** ([decision 0281](docs/decisions/0281-palette-map.md)): the painter keeps the palettes (`paint::PaintStore::palettes`); the scene hands a copy (`matgraph::Palettes`, with a key) to the graphs' registry (`GraphStore::set_palettes`, from `Scene::with_paint`, `with_graphs` and `Edit::SetPalettes`), so everything working a project's graph out through its registry sees them. The evaluator gives them to each `Job` (and own boxes' insides, `Given::palettes`); boxes whose kind `uses_palettes` hash their key, so a palette edit remakes only them (and graph fills whose graph uses one). The **Palette map** box (`matgraph::boxes::palette_map`) names a palette in a `SettingKind::Palette` setting (`SettingValue::Palette`, a name; `SettingValue` is no longer `Copy`). Pasting into another project carries the palettes boxes name (`scene::Clipping::palettes`, the canvas's `Copied::palettes`) and adds those the project has none of by name (`paint::palette::missing_from`) in the same undo step. File format 106.
- **Painted boxes** ([decision 0282](docs/decisions/0282-painted-box.md)): a box's paint is a `matgraph::Painting` (the painter's 64-pixel RGBA tiles, shared, with a key hashed from its pixels) on `GraphBox::painting`, kept only by kinds that `takes_painting`, changed by `GraphEdit::SetPainting`, given to the job (`Job::painting`) and in its cache key. The **Painted** box (`matgraph::boxes::painted`) samples it to the job's size, wrapping, and gives only its Kind's output (`BoxType::why_empty` words the refusal for the others). The Material editor's painting view (`ui::material::paint_canvas`) turns the mouse into the painter's `BrushEvent`s; `workbench::box_painting` paints them with the painter's `BrushSettings` through `paint::flat::paint_wrapped_dab` on a `StrokeCanvas` over `paint::Image::from_painting`, and sends one `SetPainting` when the stroke ends. `scene::memory` counts only the tiles a change doesn't share. File format 107 (`fileio::project::v107`: the pixels packed with zstd); graph and box files 3.
- **Image to material** ([decision 0284](docs/decisions/0284-image-to-material.md)): a photo is a `matgraph::Photo` (sRGB bytes of any shape up to 2048 pixels, its name, the packed JPEG it is saved as, a key hashed from its pixels) on `GraphBox::photo`, kept only by kinds that `takes_photo`, changed by `GraphEdit::SetPhoto`, given to the job (`Job::photo`) and in its cache key. `matgraph` never reads files: `fileio::image_file::read_photo` reads through the existing image reader, makes it at most 2048 pixels, packs it as a JPEG and takes the pixels from that JPEG (so saving and opening change nothing). The **Image** box samples its chosen square; **Even out light**, **Make seamless**, **Guess height** and **Guess roughness** (`matgraph::boxes`, shared maths in `boxes::photo_maths`) turn it into a material. The interface (`ui::material::from_photo`) asks for a picture with `WorkbenchAction::ChoosePhoto` (the app's open dialog) and gets it back through `Workbench::set_box_photo`; **Make into material** is one undo step of plain graph edits. `scene::memory` counts a photo only when a change's before and after don't share it. File format 108 (`fileio::project::v108`: the name and the JPEG); graph and box files 4, packed bytes base64 text in JSON.
- **Stamp images** ([decision 0285](docs/decisions/0285-stamp-images.md)): a Stamps box's pictures are a `matgraph::Stamps` list (`stamp.rs`: each `Stamp` sRGB bytes with straight alpha up to 512 pixels, its name, the packed PNG it is saved as, a key; a weight 1 to 10 each; at most 16 and 8 MB packed) on `GraphBox::stamps`, kept only by kinds that `takes_stamps`, changed by `GraphEdit::SetStamps` (the whole list, pictures shared), given to the job (`Job::stamps`) and in its cache key. `fileio::image_file::read_stamp` reads through the existing image reader keeping the see-through parts and packs as PNG (exact on saving and opening). The **Stamps** box (`matgraph::boxes::stamps`) places copies with Scatter's `scatter::placing`, picks a picture per copy from its own hash (the placing's random order untouched), blends copies in rank order and presses them onto a material plugged in. The interface (`ui::material::stamp_rows`) asks for a picture with `WorkbenchAction::ChooseStamp`; the app hands it back through `Workbench::add_box_stamp`. File format 109 (`fileio::project::v109`), graph and box files 5.
- **Stylised light** ([decision 0286](docs/decisions/0286-stylised-light-boxes.md)): Toon bands, Painted highlight and Colour steps (Colour), one file each in `matgraph::boxes`. Toon bands works the light out as Directional light does (its `slope_normal` and `shadow`, and `light::lit` at its softest) and cuts it into bands (`toon_bands::banded`); Painted highlight finds edges as Edge highlight does and lights those facing `light::sun`'s direction; Colour steps takes any kind with `moving::plugs` and cuts colours per channel or in Oklab lightness (`palette_map::from_oklab_kept` keeps lightness, making colours less strong to fit). Toon bands and Colour steps reuse Palette map's `nearest` and Bayer `bayer` for palettes and dither.
- **Pixel-art output** ([decision 0287](docs/decisions/0287-pixel-art-output.md)): the Pixelate box (`matgraph::boxes::pixelate`, Finish) cuts any kind into a grid of squares starting at the texture's corner (`cell_of`), every map of a material on the same squares, and limits colours, tidies and outlines on the grid. A Pixelate box feeding Material out makes the graph pixel art (`matgraph::pixel_grid`): `fileio::export::graph_textures` writes the set at that many texels (`SetOptions::pixels`, one texel from each square's middle) and Godot's material reads them crisp (`GodotCard::crisp`); `Evaluator::material_on_model` lays it by the nearest pixel (`Value::repeated_as`), as the preview does (`laying::laid(…, crisp)`). A model export's `ExportOptions::crisp` (the Export window's Crisp pixels) writes a nearest glTF sampler (`gltf::sampler_filters`).
- **The weathering set** ([decision 0288](docs/decisions/0288-weathering-set.md)): Dirt, Rust, Edge wear, Dust and Water streaks (`matgraph::boxes::weathering`, the Weathering group) each read the model's maps themselves: a box names the maps it reads with `BoxType::model_maps` (the From the model boxes return theirs), and `model::is_from_model` / `maps_needed` ask that, so the evaluator works such a box (and what it feeds) on the model's texture square, the painter bakes its maps, and own boxes and the export check treat it like a From the model box. `weathering::Follow` weighs the model's maps (the stand-in with no model) against the material's own curvature, occlusion and normals; `weathering::coated` lays a coat (colour, roughness, metal, a raise bending the normals) by how much covers each place. Water streaks find the strongest start uphill in jumps doubling in length, along the model's Up map or down the texture.
- **Trim sheets** ([decision 0289](docs/decisions/0289-trim-sheet-box.md)): the Trim sheet box (`matgraph::boxes::trim_sheet`, Finish) lays up to eight materials as horizontal strips. The project's trim rows (`scene::TrimSheet`, decision 0106, kept from the bottom) reach the graphs as `matgraph::TrimRows` (from the top, with a key) the way the palettes do: `Scene::share_trim` (from `with_trim`, `with_graphs` and `Edit::SetTrim`) calls `GraphStore::set_trim_rows`, the registry carries them (`Registry::trim_rows`), the evaluator hands them to each job (`Job::trim_rows`; `Given::trim_rows` inside own boxes) and hashes their key into boxes that `uses_trim_rows`. `trim_sheet::layout` places the strips (on the rows, or by their own heights), the box mixes every map row by row by how much of each pixel row a strip or the gap covers, sinks edges into gaps and bends normals, occlusion and curvature by the sink. `matgraph::is_trim_sheet` (a Trim sheet feeding Material out) makes the painter's graph fills (`workbench/paint_graphs.rs`) and the Material preview lay the graph once across the texture square, ignoring the real-world size and Tiling; graph fill keys hash the rows' key when the graph reads them. `ui::material::trim_rows` draws where the strips lie and sets the scene's rows from them (`Command::SetTrim`).
- **The material health check** ([decision 0290](docs/decisions/0290-material-health-check.md)): `matgraph::health::check(registry, graph, evaluation, others)` reads the evaluation the canvas's pictures already made (Material out's material, and each cut strip's material through the box feeding it) and the graph, and gives `Warning`s in plain words with `Remedy`s; `Action::edits` turns a remedy into graph edits. Measures are plain picture maths (`health/measure.rs`: light against physically based lines, lightness shaded by the normals averaged as mipmaps are, the four slowest waves of a repeat, lines across). `ui::material::health` draws it last in the preview panel, works it out again only when the pictures' number, the graph, the registry or the project's other pixel-art graphs change, and carries a remedy out through `MaterialEditor::run` (one undo step, tidied), the canvas's framing, or `Command::SetTrim` (shared with the Trim sheet's Attributes, `trim_rows::make_rows`). `SeamCheck` treats a join stepping pixel for pixel like a line inside as no seam, and `across_only` leaves a trim sheet's top-bottom join out.
- **Bypass and reroute dots** ([decision 0278](docs/decisions/0278-bypass-and-reroute-dots.md)): `GraphBox::bypassed` (`GraphEdit::Bypass`) makes the evaluator pass a box's inputs to its outputs instead of running it (`matgraph::eval::bypass`: `passed_through` picks each output's input, by kind then by conversion), under a key made only from what it passes on, so a bypassed moving box never fills the cache while the preview plays; the boxes after an empty output refuse with `Fix::StopBypass`. Reroute dots are kept beside the wires, by the input each goes into (`Graph::bends`, `GraphEdit::SetBends`), dropped with their wire and moved by `MoveBoxes` when both ends move; the ui's tidy layout (`ui::material::tidy`) moves them with their boxes and keeps them between the ends. Format 104 stores both (`project/v104.rs`).
- **Starter graphs** ([decision 0264](docs/decisions/0264-starter-graphs.md)): ready-made graphs ship as **graph files** (`fileio::graph_file`, `.matgraph`, JSON: a graph stored as `project::v95` stores it, with its own boxes as `project::v98` does) in `crates/fileio/starters/`, embedded in the app (`fileio::starter_graphs::STARTERS`, each with a 128-pixel card picture) and read through the same checked, fuzz-tested reader as any graph file. The files are written from recipes in the tests (`UPDATE_STARTERS=1`), which lay each step out in a comment frame with room for its note; the ui draws frame notes on the canvas. Opening one copies it into the project (`ui::material::MaterialEditor::open_starter`: `GraphFile::fitted_to` the project's own boxes, then `Command::SetOwnBox`s and `Command::AddGraph` as one undo step).
- **Saving:** `fileio`'s project format 95 stores each graph in a file model of its own (`project/v95.rs`); reading rebuilds it through `Graph::from_parts`, which checks everything (ids, wires, loops, places, limits) and keeps settings in range. Format 96 adds gradient settings (`project/v96.rs`); format 97 graph fills and shown settings (`project/v97.rs`); format 98 the project's own boxes (`project/v98.rs`, read so each comes after the own boxes inside it); format 99 graph fills' Tiling (`project/v99.rs`); format 100 drawn shapes (`project/v100.rs`); format 104 bypassed boxes and reroute dots (`project/v104.rs`).

## Security

- Files from strangers are hostile: every reader checks sizes before allocating and has a fuzz test. Project files are held to one limits rulebook (`fileio::limits`, [decision 0045](docs/decisions/0045-limits-for-files.md)): a cap on the unpacked body, a memory budget every list is paid from while it is read (`Bounded`), and counts of objects, edits and polygons. Shapes can't grow past `scene::MAX_SHAPE_POLYGONS` through their edits.
- No usernames or local paths are written into exported files. No telemetry.
- Dependencies are audited for licenses and known vulnerabilities on every change (`cargo deny`).

## Checks

Automatic checks, in `.github/workflows/`:

- **Every pull request and every change to main** (`ci.yml`): formatting, clippy, the tests on Windows, Linux and macOS, the API docs, the window and GPU tests on a virtual screen (`tools/smoke/window-smoke.sh`), licences and known vulnerabilities (`cargo deny`), release builds, and a changelog entry when code changes.
- **Every pull request: exported files checked by other programs** (the `gltf-check` job in `ci.yml`). `fileio`'s ignored test `files_for_outside_checkers` writes sample `.glb` files (every primitive side by side, each on its own, an edited shape with materials, Godot's collision names, and collision in parts) into the folder in `GLB_CHECK_OUT`. The Khronos glTF Validator (`tools/gltf-check/validate.cjs`, the npm package `gltf-validator`, pinned) fails the job on any error and prints warnings; then a pinned Godot (downloaded from Godot's releases and checked against its SHA-512) imports them headless into a fresh project (`tools/gltf-check/godot-import.sh`), failing on any import error, and opens each imported scene to check it holds meshes and that the collision names became collision shapes, the parts included (`check-scenes.gd`). The files are kept as an artifact.
- **Every night, and by hand** (`heavy.yml`): the heavy-mesh check (`tools/heavy/heavy-check.sh`, [decision 0033](docs/decisions/0033-heavy-mesh-safeguard.md)) on main, its numbers on the run's summary page and kept as an artifact for 90 days. It still runs by hand at every phase gate.

To run the export checks locally (Node.js and a Godot 4 program needed):

```
GLB_CHECK_OUT=/tmp/glb cargo test -p fileio --lib files_for_outside_checkers -- --ignored
npm install --prefix /tmp/validator gltf-validator@2.0.0-dev.3.10
NODE_PATH=/tmp/validator/node_modules node tools/gltf-check/validate.cjs /tmp/glb
tools/gltf-check/godot-import.sh path/to/godot /tmp/glb
```
