# 0287. Pixel-art output: the Pixelate box and crisp textures in the game

- **Status:** Accepted
- **Date:** 2026-11-13

## Problem

Phase 12's ninth extra (milestone 24, [decision 0269](0269-material-extras.md)): **pixelate to a chosen size and limit the colours to a palette**, for pixel-art games. That is two things: a box that turns a material into a few big pixels (colours from a palette, tidy, optionally outlined), and getting those pixels **into the game unchanged**: the textures written at exactly the pixel count, one texel a pixel, and the engine told not to smooth them. The preview should show them crisp too, and the texture budget should explain pixels per metre, since pixel size is a choice of look, not a lack of sharpness.

## Options

- **Where the grid lives.** Working the whole graph out at the pixel count (16 to 256 across) would make every box before it look wrong (noise at 16 pixels is mush). Instead the graph is worked out at its usual size and **cut into squares** at the end: each square takes the **average** of the picture under it (the standard: thin lines become a blend, then a palette swatch) or its **middle** pixel (crisper, but lines can vanish or double). Both make flat squares; the export then takes one texel from each square's middle, so nothing is blended.
- **Pixel counts.** A free number would let the 4 × 4 dither pattern break at the texture's edge (it must repeat a whole number of times). The Pixels setting is a list of multiples of four common in pixel art: 16, 24, 32, 48, 64, 96, 128, 192, 256 (32 to start). Squares start at the texture's corner and a picture of any size holds whole squares (`cell_of`, `cell_span`), so the result tiles square for square.
- **Palette, dither, tidying and outline on the squares.** Chaining Pixelate → Colour steps or Palette map would dither and snap per screen pixel, breaking the squares. So Pixelate does them itself, **on the grid**: Palette map's Nearest snap (Oklab) with its 4 × 4 dither laid on squares; **Tidy stray pixels** gives a square unlike all eight round it (a lone speck) the colour, and every other map, of the neighbour most squares round it match (dithering's checks have matching corners, so they are kept); **Outline** draws a one-square line on the shape's edge or just outside it, from the Outline from plug, else the material's opacity, else its height, at a level. An outline outside a see-through shape is made solid, as sprite outlines are; with a palette the outline colour is snapped too, so every colour is the palette's.
- **When the export writes the pixel count.** Any Pixelate in the graph would be ambiguous (several, or boxes after it working on screen pixels again, such as Material from height after a pixelated height, whose normals then change inside each square). The rule is simple and visible: **a Pixelate box plugged straight into Material out** (and not bypassed) makes the graph pixel art (`matgraph::pixel_grid`). The budget and export say so; bypassing it goes back to a smooth export.
- **Crisp in the engine.** Godot: the texture set's material file gets `texture_filter = 2`, `TEXTURE_FILTER_NEAREST_WITH_MIPMAPS` (sharp squares up close, the blended smaller copies far away, so they don't shimmer; Godot's own documentation recommends it for this), checked against Godot's class reference. A model's glTF gets a **nearest sampler** (magFilter `NEAREST` 9728, minFilter `NEAREST_MIPMAP_LINEAR` 9986): Godot's glTF importer turns exactly that into `TEXTURE_FILTER_NEAREST_WITH_MIPMAPS`, and Unity's glTFast into the Point filter (both checked in their source code, not tried in the engines here). Unreal Engine's glTF importer wasn't checked; the manual says to set its texture group to 2D Pixels (unfiltered). An OBJ and loose PNGs can't carry a filter: the manual says what to set in each engine.
- **A switch for the model export.** A painted model can be pixel art without any graph (painted at 64 pixels), so the model export's crisp setting is the Export window's **Pixel art → Crisp pixels** chip (not a preset's setting: kept when Made for changes, remembered with the other export settings). A texture set exported from a pixel-art graph is crisp by itself.
- **Exactly the pixel size on a model.** A graph material on a model is laid by the model's UVs and its real-world size, so its squares land wherever they fall on the model's texture. It is laid **crisp** (nearest, no blend at the squares' edges, `Value::repeated_as`), and the graph fill's settings say how many texels a pixel that makes and which texture size would give one texel a pixel. Resizing a texture set to it isn't built (the painter has no resize).
- **Preview.** The 3D preview lays the material crisp, and the flat preview draws its squares with nearest magnification, so big pixels stay sharp squares however large they are drawn. A shader that snaps to texels was considered and left: the laid texture is finer than the screen in the preview, so nearest laying is enough.

## Decision

- **Pixelate** (`pixelate`, Finish, before Material out): Transform's plugs (Height, Colour, Material in and out) plus **Outline from** (a shape); settings **Pixels** (16 to 256, 32), **Each pixel takes** (The average, The middle), **Limit to a palette** (off), **Palette**, **Dither**, **Tidy stray pixels** (off), **Outline** (None, On the edge, Outside the edge), **Outline colour**, **Outline level** (0.5). A whole material's maps are cut on the same squares; normals averaged and made a unit long. Refuses in plain words when an outline has no shapes to follow (only a colour plugged in), and like Palette map when a palette is needed and missing.
- **`matgraph::pixel_grid(registry, graph)`**: the pixel count when a Pixelate box (not bypassed) feeds Material out directly.
- **Export textures…**: a pixel-art graph's set is worked out at the Texture size and written at exactly the pixel count (`SetOptions::pixels`, `written_size`, one texel from each square's middle); Godot's `.tres` gets `texture_filter = 2` (also with the Export window's Crisp pixels on).
- **Model export**: `ExportOptions::crisp` (the Export window's Pixel art row, glTF only) writes the nearest sampler; graph fills of pixel-art graphs are laid crisp on the model; the graph fill's settings say how the pixels land.
- **Budget**: for pixel art it counts the big pixels (its maps at the pixel count), gives pixels a metre and how many centimetres each pixel covers, and asks for the same pixels a metre on every pixel-art material; it doesn't call pixel art blurrier than the project aims for.
- **No new keys or mouse actions.** No file format change: the box's settings are existing kinds; the export settings gain `crisp`, read as off from settings saved before it.
- **No starter graph:** a Pixel stone made from Stone tiles plus Pixelate reads well, but adds a card and a recipe for one box at the end of an existing starter: the manual's walk-through does it in two steps instead.

## Consequences

Any graph becomes pixel art by putting Pixelate last; turning it off (bypass) gives the smooth material back. The palette guarantee holds end to end: with Limit to a palette, every texel written is one of its swatches (tested), outline included. The dither tiles because pixel counts are multiples of four. Pixelate is cheap (one pass per map; the tidy and outline passes are on the grid). Milestone 27's health check could warn about a pixel-art material whose pixels a metre differ from the others'; milestone 28's preview options could add a viewport-wide crisp switch for painted pixel art (the main viewport still shows painted textures smoothly).
