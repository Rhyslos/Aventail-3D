# 0281. Palette map: material graphs coloured with the project's palettes

- **Status:** Accepted
- **Date:** 2026-11-13

## Problem

Phase 12's fourth extra (milestone 19, [decision 0269](0269-material-extras.md)): a **Palette map** box that colours greys with one of the project's palettes (the painter's, [decision 0183](0183-colour.md)), so every material keeps to the game's colours, and follows when a palette changes. The brief asked for: choosing a palette, a plain refusal with fixes when it is missing (after pasting into another project, say), what pasting between tabs does with palettes, three ways of mapping (steps, smooth, nearest), order and range, dithering only if simple, the box following palette edits, and a **Snap to palette** option on Gradient map if it fits cleanly. No keys.

## Options

- **How a box names a palette.** Palettes have no ids, only a place in the list and a name. By place breaks when one is deleted or moved; by name survives both and reads in files and in Attributes. A copy of the colours inside the box would never go missing, but then the box no longer follows the palette, which is the point.
- **How the palettes reach the box.** Through a separate argument to every place a graph is worked out (the canvas's pictures, the preview, the painter's graph fills, exports, own boxes), or carried by the project's **registry**, which every one of those already takes (decision 0263: "use the project's registry").
- **A box from another project naming a palette this one lacks, or has with other colours.** Leave it refusing; bring the palette along; bring it under a new name ("Moss 2") when this project's differs; or use this project's palette of that name.
- **Snap to palette on Gradient map.** A second palette setting on Gradient map with an "off" value, or a Palette map set to Nearest after it.
- **Nearest by what distance.** Plain sRGB distance (cheap, but greens and blues judged badly), or Oklab (distances match how different colours look; a few cube roots a pixel).
- **Dithering.** Error diffusion (looks best, but each pixel waits for the one before, so it is slow and doesn't tile), or a fixed 4 × 4 ordered pattern (one line of maths, tiles at every size the app uses).

## Decision

- **The box:** **Palette map** (`palette_map`, Colour group; `matgraph::boxes::palette_map`). Inputs **In** (a height) and **Colour**, neither needed alone but one is (`needs_an_input`); output **Colour**. Settings: **Palette** (`palette`, a new `SettingKind::Palette` holding a `SettingValue::Palette(name)`; no name is "First palette", whichever is first in the colour picker's list, so a new box works at once), **Mode** (`mode`: Steps, Smooth, Nearest), **Order** (`order`: As listed, Reversed, Dark to light (standard: dark greys take the darkest swatch whatever the palette's order), Light to dark), **First swatch** and **Last swatch** (`from`, `to`, 1 to 1024, counting as the colour picker shows them; past the end is the last, the other way round reverses), **Dither** (`dither`, 0 to 1).
  - **Steps:** the greys cut into as many even bands as there are swatches. **Smooth:** the swatches spread evenly from black to white and blended between. **Nearest:** each colour becomes the closest swatch in **Oklab**. With only a colour plugged in, Steps and Smooth use its lightness; with only a height, Nearest snaps its greys.
  - **Dither:** the fixed 4 × 4 ordered (Bayer) pattern, pushing the grey (Steps) or the colour (Nearest) before the swatch is picked. It repeats every four pixels, so it tiles; it is the classic pixel-art look. Error diffusion was left out as slow and not seamless.
- **Palettes by name, carried by the registry.** `matgraph::Palettes` (the palettes, shared, with a key that changes with any of them) lives on `Registry` (`palettes`, `with_palettes`); `GraphStore::set_palettes` gives the project's registry a copy, and the scene calls it whenever the painter's palettes change (`Edit::SetPalettes`, undo and redo too) and when a project is opened. Every place that works a project's graph out already uses that registry, so they all see the same palettes. The evaluator hands them to each job (`Job::palettes`) and to the inside of your own boxes (`Given::palettes`); a box whose kind reads them (`BoxType::uses_palettes`: a palette setting, or an own box holding one) hashes their key into its result's key, so **changing a palette makes only those boxes again**. The painter's graph fills hash it too, only when their graph uses a palette (`matgraph::palettes::uses_palettes`), so other layers' made keys don't change.
- **Refusals:** a project with no palettes ("… this project has none yet", fix **Add the starter palettes to this project**, `Fix::AddPalettes`, one undo step); a palette not in the project ("The palette Lava isn't in this project: it was deleted or renamed, or the box came from another project.", fixes **Use the palette …** for up to six of the project's palettes with colours, `Fix::UsePalette`); an empty palette (the same fixes). Attributes' list says "Lava (not in this project)".
- **Pasting between tabs brings the palettes along by name.** Objects (`scene::Clipping::palettes`, `PastePlan::palettes`) and boxes copied on the canvas (`Copied::palettes`) carry the palettes their boxes name (inside own boxes too, `palettes::names_in`); pasted where the project has **no palette of that name**, it is added in the same undo step. Where the project **has one of that name**, that one is used, whatever its colours, and nothing is added: a palette is the game's colours, so a material moved into another game takes on that game's palette (the status bar says so on the canvas). Identical palettes are reused by the same rule. "First palette" isn't a name and brings nothing: it follows the receiving project's first. Too many palettes (more than 64) refuses the paste with why.
- **Snap to palette on Gradient map: not added.** A Palette map set to **Nearest** after a Gradient map does exactly that, with the order, range and dither options too; a second palette setting on Gradient map would need an "off" value no other palette setting has. Gradient map's "usually comes next" now lists Palette map, and the manual gives the recipe.
- **Own boxes:** a palette setting can be one of your own box's sliders; it starts at the palette chosen inside (`SettingKind::Palette { standard }`), so making a box never changes the picture.
- **Variations** hold a palette setting when it is shown in the painter, like any setting; the dice don't touch it. **Find in the graph** finds a Palette map by its palette's name. "Change in the game" doesn't offer it (a palette isn't a number the game can change).
- **Saved:** file format **106** (`fileio::project::v106`; `v95::ValueV95::Palette`). Graph files and box files read format 2 and write it only when a setting names a palette, so files without one still open in older apps. Names longer than 200 characters are cut down when read.
- **Controls:** none new (decision 0028): a list in Attributes and fix buttons.

## Consequences

Every material can keep to the game's colours, and recolouring the game is one palette edit: each Palette map, on the canvas and on painted models, follows. Palettes stay the painter's, edited in one place. `SettingValue` is no longer `Copy` (it holds a name), so code passing setting values clones them. Graph and box files don't carry palettes yet: one opened in another project refuses until a palette is chosen, with the fixes above (the library browser, milestone 29, could bring them along). Milestone 24 (pixel-art output) can build on Nearest and Dither.
